## WM redesign v2 (2026-08-24) — richer per-OS daemons, keyboard side only

Why: Ben built a working Python daemon on the Windows machine (PoC/discovery
effort, not sacred) that proves out directional window focus, window swap,
resize, a screen-position window cycle, minimize-based fake workspaces, and
~25 named placement regions — all driven by `RegisterHotKey` on `F13`-`F24`
+ modifiers, verified on real 3-monitor hardware. That's strictly more than
native `Win`+arrow snapping ever offered, so `WM_Win` no longer needs to
lean on native chords for anything the daemon can do better. Separately,
this session worked out what's realistically buildable on macOS via
Hammerspoon to replicate the same feature family (findings below) — no
macOS daemon exists yet, this pass only rebuilt the keyboard layer that
targets one.

**Explicit scope call: keyboard layer first, OS-side tools second.** No
Hammerspoon Lua got written, no Python daemon config got touched. macOS and
Windows stay **separate, independent WM layers** — not merged — until both
stabilize. macOS **drops workspace-switch/assign/unassign/show entirely**:
Mission Control already covers the need, and Hammerspoon's
`hs.spaces.moveWindowToSpace` is confirmed broken on Sequoia (open upstream
issue #3698, fix unmerged) — reimplementing workspaces via real Spaces was
never on the table, and a second minimize-based fake-workspace system on
top of Mission Control wasn't judged worth it either.

**v2.1 (same day): mirroring dropped, one hand per domain.** The first pass
kept v1's mirroring for the 3 anchor diamonds (focus, place-half, swap) —
24 of the board's positions spent on letting either hand reach the same 12
actions. Fair question raised in review: that traded a lot of room for a
benefit (act with whichever hand is free) that the Magic-latch entry
already provides independent of mirroring — momentary-hold's real,
non-redundant value is just "quick tap without fully latching," which only
needs *a* free hand, not *either* hand. So v2.1 gives each hold key a fixed
domain instead of identical content: **hold `G` → right hand acts →
right hand = movement** (place, swap, resize), **hold `H` → left hand acts
→ left hand = focus** (focus-direction, focus-monitor, focus-toggle,
cycle). This was free to do — the Cursor-layer arrow alignment that pins
place-half to positions 31-34 only constrains the *right* hand; Cursor's
left hand does unrelated home-row-mod stuff, so the left hand's row2 was
never actually locked. Net effect: 24 positions back, zero coverage lost,
`G`/`H` themselves are `&trans` again (v2's first pass had borrowed them
for 2 workspace actions; no longer needed). Windows still 41 actions /
41 positions now (was 41/53), macOS still 27/27 (was 27/39) — same
catalog, no duplication. The authoritative position table is
`data/wm-actions.js`'s own doc comment now, not the table below this
paragraph (which is v2-first-pass and stale) — that file is regenerated by
the same two edit scripts, so it can't drift the way a second copy in this
file would.

**Hammerspoon capability findings that shaped the macOS half of the
catalog:**

| capability | verdict |
| --- | --- |
| Directional focus | `hs.window:focusWindowWest/East/North/South()` exists but has two open correctness bugs (#2558 wrong-app-focus, #3574 hangs) — plan on a hand-rolled port of the Windows daemon's own proven algorithm instead |
| Placement | `hs.window:moveToUnit()` — solid, native, use it |
| Move to screen | `hs.screen:toWest/East/North/South()` + `hs.window:moveToScreen()` — real; not `next()/previous()` (non-spatial order) |
| Swap | no builtin — hand-roll via two `setFrame()` calls, self-inverse, same as Windows |

| Minimize/restore | `hs.window:minimize()`/`:unminimize()` — standard, reliable |
| Hotkeys | `F13`-`F20` bindable with any modifier, no OS collisions (already proven — `WM_practice` shipped F13-F20 since 2026-08-23). `F21`-`F24` don't exist on macOS at all (no Carbon virtual keycode, see §F20 ceiling below) — Windows has no such ceiling, the daemon verified all of `F13`-`F24` bare and with Ctrl |

**Architecture: mirroring dropped for the expanded catalog, entry mechanism
unchanged.** v1 mirrored all 12 actions onto both hands. At 27 (macOS) /
41 (Windows) actions that's no longer possible without doubling the
position budget, so each action now lives on one hand only — except three
"anchor" rows (focus-direction, place-halves, swap; 12 actions) which stay
mirrored because it was cheap and keeps the single most valuable v1
property (fast either-hand access to the highest-frequency actions).
`&WM_hold_v1`/`&WM_hold_H_v1` (momentary hold-`G`/hold-`H`) and the
Magic-key latch (`&to 14`/`&to 15`) needed **zero changes** — both already
work identically regardless of how many actions live on the target layer.

**Minimize/restore, reinstated.** Neither the Windows daemon's action list
nor the first-draft macOS list named these. Windows didn't need a new
binding — `LG(DOWN)`/`LG(UP)` at the unchanged row-2 positions already

common than a third/fourth place-quadrant, this design drops NE/SW
quadrants (keeps NW/SE) to make room for dedicated minimize/restore at the
same shared position on both layers.

## The idea — three tiers collapsed to one

The original plan was three layers emitting three different things, because
F-keys needed software that couldn't be installed everywhere:

| ~~Tier~~ | ~~Layer~~ | ~~Emits~~ | ~~Where~~ |
| --- | --- | --- | --- |
| ~~Native Windows~~ | ~~`WM_Win`~~ | ~~`LG(...)` chords~~ | ~~work laptop~~ |
| ~~Native macOS~~ | ~~`WM_macOS`~~ | ~~hyper chords → App Shortcuts~~ | ~~Mac, pre-WM~~ |
| Full WM | `WM_Universal` | `F13`–`F24` | everywhere |

**Both machines now have software that consumes F-keys directly** — Rectangle
on the Mac, PowerToys on the work laptop (installed 2026-08-09). So there is
one layer emitting F-keys, and the per-machine difference moves out of the
keyboard and into each tool's config, which is where it always belonged. The
keys under the fingers never change, and now neither does what they emit.

**This deletes stages 4 and 5.** No `WM_macOS`, no `WM_Win`, no hyper chords,
no `LG(...)` chords, no duplicated base layers, no tier switch on the Magic
layer. `WM_practice` *is* the layer — it just needs renaming.

It also removes the practice harness's one fidelity gap. The old note that
"the native tiers can never be drilled in a browser, because the OS eats
`Win+Left` and hyper chords first" no longer applies to anything: everything is
an F-key, and browsers see those cleanly. The drill is now full-fidelity for
the real thing.

Per machine:

| | tile / verbs | move to display | switch desktop |
| --- | --- | --- | --- |
| macOS | Rectangle | Rectangle | macOS Mission Control shortcuts |
| Windows | PowerToys FancyZones | FancyZones | native, via Keyboard Manager |

Note neither tool does **directional focus** ("focus the window to my left") —
Rectangle moves and resizes the focused window, FancyZones snaps it. That gap
is what §7d's little Python tool was for, and it survives the collapse.

### Physical arrangement

Mirrored, so either hand can drive while the other holds the layer:

```
           hold G -> right hand        hold H -> left hand
travel     [ mon← ] [ desk← ] [ desk→ ] [ mon→ ]     U I O P  /  Q W E R
tile       [  ←   ] [   ↑   ] [   ↓   ] [  →   ]     J K L ;  /  A S D F
verbs      [ full ] [center ] [  min  ] [restore]    M , . /  /  Z X C V
```

**No close key, on purpose.** F23 was "close window" until it turned out to sit
on the *same finger* as snap-down (F19), one row below it — right hand `.` under
`L`, left hand `C` under `D`. A slightly low snap-to-bottom-half closed the
window. That's the one irreversible action in the set, parked under the one
you'd reach for most, on a layer you enter by holding a letter. Minimize took
the slot: it's the verb that was actually missing, and it's undoable.

Closing stays on `Cmd`/`Ctrl`+`W` where it already lives. If you ever do want it
here, note there is no F25 — a 13th action needs a modified F-key like
`LS(F21)`, which the detector in `js/wmjoin.js` doesn't match (it looks for a
bare `F13`–`F24` tap keycode). Budget an hour, not a minute.

**Spatial copy, not finger mirror.** Both hands read left-to-right. A true
same-finger mirror would put `←` under the left index and `→` under the left
pinky, so the leftmost key would move a window right — which breaks the
one-spatial-map principle the whole layer exists to uphold. Flip `MODE` in
`tools/edits/wm-mirror-gh.js` to `'finger'` if you'd rather train same-finger.

The tile row is `← ↑ ↓ →`, **not** vim order — it matches the `Cursor` /
`Cursor_macOS` layers' existing arrows on 31–34, and the Mouse layer agrees.
Changing it means changing all of them, not just this layer.

**CORRECTION.** An earlier finding claimed the `Cursor` layer "mirrors 10
actions across both hands," and used that as precedent. It doesn't. Its left
hand is home-row modifiers (`LGUI`/`LALT`/`LCTRL`/`LSHFT`) plus two select
macros; the arrows exist only on 31–34. There was no precedent — the spatial
call above was made on the principle, not on prior art.

### How the layer latches

**CORRECTION, and it matters.** The original §5 said: hold `G`, tap the left
thumb, and the layer latches so you can let go. **ZMK cannot do this.**
`zmk_keymap_layer_toggle` is a plain bitmask test with no refcounting:

1. Hold `G` → `&mo 14` → layer 14 **on**
2. Tap #56 → `&tog 14` sees layer 14 already active → **deactivates it**
3. Release `G` → `&mo` release deactivates again (no-op)

You land on the base layer mid-hold. A toggle can only latch a layer that is
currently *off*, so the entry has to be reachable without holding the layer.

**What actually works:** hold the Magic key, tap `H` (#30) — that's `&to 14`,
which switches to the layer and turns everything else off, with no hold. `&to`
targets a different layer than the one being held, so the Magic key's release
doesn't undo it. Exit with #56 or the #0 panic key.

So the interaction model is:

| | |
| --- | --- |
| momentary | hold `G` (right hand acts) or `H` (left hand acts) |
| latched | Magic + `H` → stays on hands-free |
| exit | #56 unlatch, #0 panic to `HRM_macOS` |

### Misfire guards — settled

Every hold-tap on the board is now `tap-preferred`, so **only the tapping term
can trigger a hold**. No amount of fast rolling turns a letter into a modifier
or a layer. Reached after typing tests kept getting derailed, in three passes:

1. Raised the thumbs' term and idle guard. Not enough — under `balanced`, a
   hold fires as soon as you press *and release* another key, even 20ms in, so
   no timing value could close it.
2. Thumbs → `tap-preferred`. Fixed the thumbs.
3. `G`/`H` → `tap-preferred`, and the index HRMs' idle guard 100 → 150.

The real finding in step 3: **all eight of TailorKey's HRMs were already
`tap-preferred`.** `&WM_hold_v1` and `&WM_hold_H_v1` were added as
`hold-preferred` for snappiness, which made them the only two keys on the board
that could fire from a roll — sitting on the home row, next to eight that
couldn't. The convention was right and the addition broke it.

The index HRMs also sat at idle 100 while pinky/ring/middle were all 150. The
index finger is the fastest and most rolled-through, so it least deserved the
weakest guard; treated as an oversight and levelled up. The tapping-term
gradient (280/240/210/190 by finger) is deliberate and untouched.

| | term | idle | flavour |
| --- | --- | --- | --- |
| HRM pinky / ring / middle / index | 280 / 240 / 210 / 190 | 150 | tap-preferred |
| space | 250 | **200** | tap-preferred |
| enter, backspace, delete | 250 | 150 | tap-preferred |
| `G` | 250 | 150 | tap-preferred |
| `H` | 250 | 250 | tap-preferred |

Space carries a bigger idle guard than the other thumbs because it follows a
letter constantly, and the guard is what makes fast typing *fast*: inside the
window the tap is decided immediately, with no queue and no wait. Raising it
cures latency and misfires at once. It stops helping only when your inter-key
gap exceeds it — i.e. when you're typing slowly and don't notice.

Cost: reaching a layer now needs a deliberate hold past the term before pressing
anything. If that drags, lower the term — under `tap-preferred` that is far
safer than it was under `balanced`, because the term is no longer the only thing
between a fast roll and a misfire. Knobs are in `tools/edits/thumb-timing.js`
and `tools/edits/holdtap-tuning.js`.

### Positional guards

`holdTriggerKeyPositions` is the real guard, not timing: the hold only resolves
if the *next* key is one of the WM keys. `G`'s trigger list is the right hand
only and `H`'s is the left hand only — deliberately not merged, since a shared
list would re-open every misfire the split closes.

`H` carries more risk than `G` and has a higher idle guard to match. `H`'s
triggers include `A` and `E`, so "have", "has", "he", "her", "help" are all
h-followed-by-a-trigger, and sentence-initial "He"/"Have" follows exactly the
kind of pause that defeats a short guard. Hence **250ms** on `H` vs **150ms**
on `G`, whose triggers are right-hand only (`ge`, `ga`, `gr` are all safe;
only "go", "give", "glad", "guess" are exposed).

If `G` starts misfiring on "go", raise `IDLE_G` — don't invent a new mechanism.

## The F20 ceiling on macOS is real — resolved

**`F21`–`F24` do not work on macOS.** Tested. `F13`–`F20` have Carbon virtual
keycodes (`kVK_F13`…`kVK_F20`); `F21`–`F24` were never assigned any, so no
macOS app can bind them no matter how cleanly the keyboard sends them. Windows
handles all 24 fine — the limit is macOS only.

This took two wrong turns worth recording, because both are easy to repeat:

1. Research said "ceiling at F20" (Keyboard Maestro reports). Believed.
2. A browser test showed F21–F24 arriving, so the ceiling was written off as
   folklore. **That test proved the wrong thing** — Chrome derives `event.code`
   from the HID usage directly and never consults the Carbon table, so a
   browser sees keys that no shortcut recorder can bind.

The lesson: test against the layer that has to consume the key, not against
whatever is easiest to instrument.

**Fix, shipped:** the verb row moved from `F21`–`F24` to `LS(F13)`–`LS(F16)`.
Positions did not move — only what the caps emit. Shift because an F-key
produces no text, so shifting one has no side effect, and both Rectangle and
PowerToys bind modified F-keys without complaint.

```
travel   F13      F14      F15      F16
tile     F17      F18      F19      F20
verbs    LS(F13)  LS(F14)  LS(F15)  LS(F16)     "the travel row plus Shift"
```

Applied by `tools/edits/wm-shift-verbs.js`, which also asserts no `F21`–`F24`
survives anywhere in the layout. `js/wmjoin.js` matches both forms, and
`js/practice.js` rebuilds the name from `e.shiftKey` — `event.code` is bare
`F13` even when Shift was sent, so without that a verb key scores as its
travel-row twin.

A second reserved namespace sits on top of the tile row:
`LC(LS(F17))`–`LC(LS(F20))` belong to `tools/edits/bt-mouse-follow.js` — the
Magic-layer BT keys tap them before hopping profiles, so the machine being
left pushes the MX Master 3S to the destination host (HID++ ChangeHost via a
per-machine Hammerspoon / AutoHotkey listener). Anything else binding
Ctrl+Shift+F17–F20 would fire a mouse push.

## Things the layout already does

Written down because they predate this plan and are easy to re-invent.

**Alt-tab is already solved, three ways.** Combos on the base layers fire
`&mod_tab_chord_v2_TKZ <mod> 4`:

| chord | sends | drives |
| --- | --- | --- |
| `X` + `Home` (left ring, two rows) | `⌥`+`Tab` | AltTab |
| `V` + `→` (left index, two rows) | `Ctrl`+`Tab` | tab cycling |
| left thumb 1 + `B` | `⌘`+`Tab` | macOS app switcher |

The macro is the clever part: it activates **layer 4 (Cursor)**, presses the
modifier, taps `Tab`, then `&macro_pause_for_release` holds all of it until you
let the combo go. So the switcher stays open while your right hand has arrows on
`J K L ;`, and releasing picks. A plain "send ⌥+Tab" key cannot do this — the
modifier has to stay down. Don't move this to the WM layer: it would fight the
`G` hold, and the right hand there is F-keys, not arrows.

AltTab stores no custom `holdShortcut`, so it's on its default `⌥`+`Tab` and
already matches the first combo.

**The Typing layer** is reached from Magic → `&to 2` on #50 (bottom-row index).
Magic is re-bound on the layer itself, so that's the way back.

Its job is turning the home-row mods off: it binds the home row as plain keys
and leaves everything else `&trans`.

> **Rule that follows:** anything transparent on Typing falls through to the
> base layer. Adding a home-row hold-tap therefore punches a hole in Typing
> unless you also bind the plain key there. We did exactly that with `G` and
> `H` and didn't notice. `tools/edits/typing-layer-plain.js` derives the fix
> rather than hardcoding it — it walks the base home row, finds every hold-tap,
> and binds that key's tap side on Typing. Re-run it after any home-row change.

## When the WM layer "does nothing"

**Check the OS mode first.** It is the cause almost every time.

`WM_Win` is reachable only from `HRM_WinLinx`; `WM_practice` only from
`HRM_macOS`. In the wrong mode the layer still activates — it just emits the
other machine's keys, which that machine ignores. Nothing happens, nothing
errors, and the keyboard types normally, so it reads as "the layer is broken".

**The mode does not survive a power cycle.** `&to 1` is layer state in RAM, not
a setting. Battery death, a reset, a long enough sleep — any of them drop you
back to the default layer 0, which is `HRM_macOS`. On a Windows machine that
silently disables the whole WM layer.

Fix: hold Magic, tap **left thumb 1** (`&to 1` → HRM_WinLinx). Thumb 2 is macOS.

### Telling the three failures apart

Hold `G`, wait a beat, tap `J`, in a text editor:

| | |
| --- | --- |
| nothing at all | layer live, wrong OS mode — switch it |
| `gj` types out | hold didn't resolve — hold 250ms *before* pressing (tap-preferred) |
| window snaps left | working |

### Making it fail softer

On the Windows machine, add PowerToys Keyboard Manager remaps for `F13`–`F20`
to the same chords `WM_Win` sends. The native chords stay the primary path and
keep working with PowerToys dead; the F-keys become a fallback so the wrong OS
mode is survivable rather than silent. Costs nothing, no downside.

## Windows — how `WM_Win` works (v1 — superseded, see §WM redesign v2)

**v1 history below, kept for the reasoning.** As of 2026-08-24, `WM_Win`
targets the Python daemon (41 actions, `tools/edits/wm-redesign-win.js`),
not native `Win`+arrow chords — `tools/edits/wm-win-layer.js` is no longer
run. The "10 of 12 are native" framing below no longer applies except at
the unchanged place-half row (still native, on purpose — see §WM redesign
v2's minimize/restore note).

Layer 15, built by `tools/edits/wm-win-layer.js`. Same twelve positions, same
mirror, same finger motions — only the emission changes. `G`/`H` on
**HRM_WinLinx** point at it instead of at `WM_practice`, so the tier follows the
machine exactly like the OS switch already does. One muscle memory, two layers.

**Why a layer rather than Keyboard Manager remaps.** Not capability — KBM could
remap `F13`–`F20` to the same chords. Robustness on a locked-down machine:
PowerToys has to be running, and KBM does not apply inside elevated windows
unless PowerToys itself runs as admin, which you may not be permitted to do. A
keyboard that sends `Win`+`←` needs none of that — it works at UAC prompts, on a
fresh profile, with nothing installed.

**10 of 12 are native:**

| | |
| --- | --- |
| mon ← / → | `Win`+`Shift`+`←` / `→` |
| desk ← / → | `Win`+`Ctrl`+`←` / `→` |
| snap ← ↑ ↓ → | `Win`+`←` `↑` `↓` `→` |
| maximize / minimize | `Win`+`↑` / `↓` |

**CORRECTION.** This first shipped with only 8 native, on the belief that
`Win`+`↑`/`↓` were strictly maximize/minimize and so couldn't serve as
top/bottom half. They are **contextual**: inside an already-snapped zone they
place the window in the top or bottom half *of that zone*; on a floating window
they maximize and minimize. Source:
[Damir's Corner](https://www.damirscorner.com/blog/posts/20220121-WindowSnappingInWindows11.html).

So the tile row's up/down and the verb row's maximize/minimize send the same two
chords and let Windows decide. That redundancy is Windows' model, not a mistake —
its `Win`+arrow snapping is a state machine, not a set of absolute positions the
way Rectangle's Top Half is. Practical consequence: `snap top` gives a full-width
top half only from an unsnapped window; after `snap left` it gives the top-*left*
quarter. The finger motion still means "move it upward".

**2 have no Windows keyboard route** — center, and a restore distinct from
minimize. Snapping to a zone by name doesn't exist
([PowerToys#22338](https://github.com/microsoft/PowerToys/issues/22338), open),
and `Win`+`Ctrl`+`Alt`+number switches **layouts**, not zones — don't plan around
it. Those two stay as F-keys rather than being faked: they do nothing until
something picks them up, and the other ten work regardless. If you want all
twelve later, it's a ~50-line AutoHotkey or Python helper on those two keys
calling `SetWindowPos` — same shape as the directional-focus tool below,
plausibly the same script.

**The drill and cheat sheet target layer 14** and that's correct — they pick the
layer with the most F-keys, and the positions are identical, so drilling the
macOS layer trains the Windows one. `wm.html` shows both layers side by side,
finding the twin by position overlap and binding density rather than by name.

## Later tooling

**Cheat-sheet popup (Rust).** The core idea is a join: the layout JSON knows
"position 31 emits F13", the WM config knows "F13 → focus left", neither knows
the other. Join on the keycode and the cheat sheet labels a *physical key
position* with a *semantic action*, staying correct when either side changes.

**The join half is done** — `wm.html` + `js/wmjoin.js` draw exactly this in the
browser, including the entry/exit keys read off the keymap. What the Rust
version would add is *floating it over your desktop without taking focus*,
which is the expensive 90%. Everything below is about that, not about the join.

- Parse GlazeWM's `config.yaml` with serde — `serde_yaml` is archived, use
  `serde_yaml_ng` or `serde_yml`.
- The hard part is a window that doesn't take focus. `winit` gives
  undecorated/transparent/always-on-top but not this. Needs raw handles:
  Windows `WS_EX_NOACTIVATE` + `WS_EX_TOOLWINDOW`; macOS `NSPanel` with
  non-activating style mask, floating level, all-spaces collection behavior.
  Budget real time — this is where these projects stall.
- Let the WM be the hotkey daemon: GlazeWM's `exec` can call
  `cheatsheet --toggle`. No global hotkey code, no conflicts.
- Run as a tray daemon with a local socket; cold start is 200ms+ and a laggy
  popup feels broken. Add `notify` to live-reload the config.
- GlazeWM will try to tile the popup — add a `window_rules` ignore entry before
  debugging window flags.
- **Do not** try to auto-detect the active ZMK layer. ZMK doesn't report layer
  state over normal HID and every workaround is fragile. The popup is triggered
  *from* the WM layer, so just show the WM layer. That constraint is what keeps
  it a weekend project.
- Extension: VS Code exports its keybindings as JSON, giving a three-way join —
  physical key → emitted chord → app action. Arguably more useful than the WM
  piece.

**Launcher ("Alfred for Windows") — mostly exists already.** The idea: fuzzy
search over open VS Code windows and applications, keyboard-summoned. Before
building anything, note what's already covering it:

- *VS Code windows*: solved in-app by the apps layer's `;` → `⌃R`
  (`openRecent`) — typing three letters of a repo focuses that window. No
  global tool needed for the main case.
- *Open windows generally*: PowerToys Run is already installed on the work
  laptop and its Window Walker plugin does switch-to-open-window by fuzzy name.
  Try that before writing code.
- *The residue*: if something is still missing after those two, it's probably a
  PowerToys Run plugin (C#, small) rather than a from-scratch app — same
  robustness caveats as Keyboard Manager (PowerToys must be running; no
  elevated windows).

**Own-WM itch, scoped honestly.** The recurring urge to build a Windows WM tool
keeps resolving into three small, separable gaps rather than one big app:
directional focus (the Python tool below), the two non-native `WM_Win` keys
(center / restore — the ~50-line `SetWindowPos` helper in §Windows), and the
launcher residue above. Building them as three tiny tools keeps each a weekend;
fusing them into "my WM" is how the project stalls. GlazeWM remains the
off-ramp if snapping is ever truly outgrown.

**Directional-focus tool (Python, only if a WM stays unavailable).** Fills the
one gap native Windows can't. `RegisterHotKey` + `GetMessage` loop, **not**
`SetWindowsHookEx`. `EnumWindows` + `GetWindowTextW` to enumerate.
`DwmGetWindowAttribute` with `DWMWA_EXTENDED_FRAME_BOUNDS` for geometry —
**not** `GetWindowRect`, which includes invisible shadow borders and breaks
adjacency math by ~7px per edge. Filter cloaked windows (`DWMWA_CLOAKED`,
attribute 14) or phantom UWP windows appear. `SetForegroundWindow` silently
fails when the process isn't already foreground — usually fine from a hotkey;
**do not** reach for `AttachThreadInput`. Algorithm: filter candidates whose
center lies in the target direction, prefer those overlapping on the
perpendicular axis, take the nearest. ~40 lines.

## Workflow

```sh
node tools/edits/<script>.js IN.json OUT.json   # scripted, reviewable edit
node tools/diff.js IN.json OUT.json             # confirm only what you meant
node tools/bake.js                              # newest layouts/ -> data/layout.js
```

Then import the JSON at my.moergo.com/go60, build, flash. Keep a pristine copy
of the working `.uf2` and `.json` outside this repo.

Rules for scripted editing: **layer references are numeric** — `&mo 6`, `&to 1`
and every combo's `layers` array are indices, so appending a layer is safe and
inserting one silently re-points everything. Never insert. `tools/diff.js`
matches layers by name specifically so a move shows up as a move.
